# E7-05.1 — Endurecimento da API e headers de segurança

Este documento registra os controles entregues no PR #197, as configurações que
precisam ser mantidas por ambiente e as evidências da validação técnica.

## Controles implementados

| Controle | Comportamento | Evidência |
| --- | --- | --- |
| Headers de segurança | Helmet remove `X-Powered-By`, aplica `nosniff`, `Referrer-Policy: no-referrer` e CSP. A API usa CSP restritiva; `/docs` usa CSP compatível com Swagger UI. | `apps/api/tests/apiHardening.test.js` |
| CORS | `CORS_ORIGIN` aceita uma lista explícita de origens. `*` é rejeitado em qualquer ambiente; em produção, a variável é obrigatória. Requisições sem `Origin` continuam permitidas para o app nativo e health checks. | Testes de configuração e requisições com origem permitida/bloqueada |
| Rate limit | Há limite global para `/api`, limites específicos para login/cadastro/rotas clínicas/admin, limite adicional para RAG e limite para `/docs`. A resposta excedente é genérica. | `apps/api/middlewares/authRateLimit.js` e `apiHardening.test.js` |
| Payload | JSON e `urlencoded` têm limite de `100kb`. Excesso retorna `413` com `payload_too_large`. | Teste de payload acima do limite |
| Autorização | Rotas clínicas continuam exigindo JWT e papel quando aplicável. A ausência do token retorna erro seguro sem acessar dados clínicos. | `securityBaseline.test.js` e teste manual de `/api/pregnants` |
| Erros | Erros internos retornam `internal_error`; respostas não expõem mensagem, stack, e-mail, IP ou detalhes do banco. | `apps/api/tests/noErrorLeak.test.js` e `apiHardening.test.js` |

## Configuração por ambiente

Em produção, configurar pelo menos:

```dotenv
CORS_ORIGIN=https://app.exemplo,https://admin.exemplo
ENFORCE_HTTPS=true
TRUST_PROXY=1
```

Não usar `CORS_ORIGIN=*`. As origens devem ser as URLs reais do cliente que
precisa acessar a API. O app nativo e os health checks não enviam `Origin` e,
por isso, não devem ser bloqueados por essa regra.

Os limites podem ser ajustados por ambiente com as variáveis já existentes,
como `AUTH_RATE_LIMIT_MAX`, `REGISTER_RATE_LIMIT_MAX`,
`CLINICAL_RATE_LIMIT_MAX`, `API_RATE_LIMIT_MAX`, `RAG_RATE_LIMIT_MAX` e
`DOCS_RATE_LIMIT_MAX`. A alteração desses valores deve ser registrada na
configuração do ambiente e revisada pelo responsável técnico.

## Validação manual local

Com a API local iniciada na porta `3014`, foram confirmados:

- `GET /ping`: `200`, sem `X-Powered-By`, com CSP e `Referrer-Policy`;
- `GET /docs/`: `200`, Swagger UI servido com CSP compatível;
- `GET /docs/openapi.json`: `200`, contrato OpenAPI servido;
- origem `http://localhost:8081`: permitida e refletida no CORS;
- origem `http://evil.example`: bloqueada com `403` e `{ "error": "forbidden" }`;
- `GET /api/pregnants` sem token: `401`;
- payload JSON acima de `100kb`: `413` e `{ "error": "payload_too_large" }`;
- 12 tentativas de login inválido: as duas últimas retornaram `429`.

Os testes usaram apenas dados sintéticos. Não foi feita alteração em dados de
produção ou homologação compartilhada.

## Aceite pendente

A validação técnica local está concluída. Para encerrar o item, o responsável
técnico/PO ainda deve registrar:

- as origens oficiais permitidas em homologação e produção;
- os limites de requisição esperados por ambiente e por rota;
- a confirmação manual de login, gráfico e documentos no build mobile de
  homologação;
- a aprovação de que as respostas genéricas atendem ao risco operacional.

Esses pontos são de configuração e aceite operacional; não exigem alteração
adicional no código do hardening já mergeado.
